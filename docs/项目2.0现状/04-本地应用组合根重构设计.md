# 本地应用组合根重构设计

日期：2026-07-16

状态：实施基线

## 1. 背景与证据

`apps/server/src/bootstrap/local-application.ts` 当前为 2,736 行、115 KB，包含 83 个直接导入，其中 50 个来自领域 Module、24 个来自持久化。`createLocalApplication()` 本体占 2,314 行，最终 `serverDependencies` 对象约 730 行。

该文件当前同时承担：

- Store 初始化、事务恢复和 Repository 创建；
- Provider、GenerationRuntime、任务恢复和运行控制；
- outbox、事件日志、事实投影及串行 flush；
- 建课、学习、教学、Review、排期、周报、画像和下一课推荐的接线；
- 教学、Review 与补充学习的画像证据检查点组装；
- HTTP RouteOptions 的大量业务 callback；
- 启动恢复顺序、degraded 状态和后台 scheduler 生命周期。

组合根应只描述对象创建顺序和生命周期。当前的大量循环、条件、错误映射、证据组装与业务流程编排已经超出组合根责任，使跨模块知识集中于单个文件，并让任何局部修改都需要理解几乎全部后端运行链。

## 2. 目标

1. 保持 `createLocalApplication(options)` 的调用方式和返回能力不变。
2. 将跨模块工作流隐藏到小 Interface、深 Implementation 的内部 Module 中。
3. 让组合根只负责 Store 恢复、按序创建 Module、汇总 `ServerDependencies`、执行启动恢复和逆序关闭。
4. 将 `local-application.ts` 降至不超过 160 行；将真正的 assembly 文件控制在 400 行以内，且不得包含业务循环或 HTTP handler 实现。
5. 每个内部运行时文件聚焦单一责任，原则上不超过 650 行；超过时必须继续按工作流拆分。
6. 用架构检查锁定新结构，避免复杂度重新回流。

## 3. 冻结边界

本次是行为保持重构，以下内容绝对不改变：

- HTTP 路径、方法、请求/响应 schema、状态码和错误码；
- `ServerDependencies` 的公开字段和各 RouteOptions Interface；
- 课程、课节、会话、Review、排期、画像和永久删除规则；
- 幂等键、资源版本、事件类型、事件 payload、Artifact 命名和本地文件路径；
- Provider 选择、fallback、任务优先级、恢复与帧日志语义；
- outbox、profile evidence 与 reasoning analysis 的串行 barrier；
- `now` 注入、随机 ID 前缀以及使用调用时实时时钟的既有位置；
- 启动恢复、degraded 状态和异常传播顺序；
- 页面文案、导航、按钮、交互时机和前端请求行为。

当前工作区正在实现的 weekly report scheduler `start()` / `stop()` 生命周期属于基线，重构必须原样保留，不得恢复为单次 `tick()`。

## 4. 方案比较

### 4.1 仅机械拆文件

把原代码块移动到多个 helper，并通过一个包含几十项字段的 context 传递全部依赖。改动风险低，但 Interface 与 Implementation 同样复杂，删除任一 helper 后复杂度不会回到少数明确调用者。这只是移动文件，不满足目标。

### 4.2 全部下沉到既有领域公共 Interface

让现有十一个领域 Module 直接吸收所有跨模块流程。长期边界最纯，但会同时扩大多个公共 Interface，并迫使领域 Module 依赖原本不拥有的 Repository、RouteOptions 或其他领域细节，形成新的跨模块耦合。本轮不采用。

### 4.3 bootstrap 内部深 Module

采用。`LocalApplication` 自身作为一个深 Module，对外只保留现有创建 Interface；内部按运行时能力拆分。内部 seam 只服务本地实现和测试，不成为新的领域公共 Interface。确实需要跨 slice 的流程由专门的 coordinator Module 拥有，而不是重新放回 assembly。

## 5. 目标结构

```text
apps/server/src/bootstrap/
├─ local-application.ts
└─ local-application/
   ├─ contracts.ts
   ├─ assemble.ts
   ├─ mock-provider-script.ts
   ├─ generation-runtime.ts
   ├─ event-facts-runtime.ts
   ├─ profile-runtime.ts
   ├─ course-runtime.ts
   ├─ learning-runtime.ts
   ├─ planning-runtime.ts
   ├─ review-runtime.ts
   └─ insights-runtime.ts
```

`local-application.ts` 是唯一公开入口，只重新导出合同并委托给 `assemble.ts`。`assemble.ts` 是组合根，只能创建 Module、按既有顺序调用生命周期方法并合并 RouteOptions；不能实现业务 callback、遍历聚合、组装证据或直接执行领域命令。

## 6. 外部 Interface

以下 Interface 保持语义兼容：

```ts
export type LocalApplicationOptions = Readonly<{
  dataRoot: string;
  csrfToken: string;
  allowedOrigin?: string;
  mockFailOnce?: boolean;
  now?: () => Date;
  runtimeIdentity?: Readonly<{
    instanceId: string;
    generation: number;
    startedAt: string;
    identityFingerprint: string;
    buildId: string;
    protocolVersion: string;
  }>;
  providers?: readonly AiProvider[];
  additionalProviders?: readonly AiProvider[];
  initialProviderId?: string;
  defaultFallbackProviderIds?: readonly string[];
  defaultMaxAttempts?: number;
  secretStore?: SecretStore;
  providerConfigRepository?: ProviderConfigRepository;
  createDiagnostics?: () => Promise<Readonly<{ artifactRef: string }>>;
}>;

export type LocalApplication = Readonly<{
  close(): Promise<void>;
  serverDependencies: ServerDependencies;
  courseRepositories: ReturnType<typeof createLocalFileCourseCreationRepositories>;
  frameLog: GenerationFrameLog;
  dataRoot: DataRoot;
  generationRuntime: ReturnType<typeof createGenerationRuntime>;
  providerConfigService: ReturnType<typeof createProviderConfigService>;
}>;

export function createLocalApplication(
  options: LocalApplicationOptions,
): Promise<LocalApplication>;
```

返回的 Repository 和运行时对象继续保留，避免破坏现有集成测试及 `main.ts`。它们是本地应用测试观察面，不扩展为 HTTP 能力。

## 7. 内部 Module 与 Interface

### 7.1 GenerationRuntime

拥有 Mock Provider 脚本、Provider 集合、GenerationRuntime、GenerationExecution、FrameLog、ProviderConfigService、启动配置恢复和 runtime control RouteOptions。

Interface 只暴露其他内部 Module 实际消费的 `runtime`、`execution`、`frameLog`、`providerConfigService`、Provider readiness 和 runtime control RouteOptions。Mock 脚本不再出现在组合根。

### 7.2 EventFactsRuntime

拥有 EventLog、EventDispatcher、FactProjector、FactRepository、Outbox 和 `outboxBarrier`。Interface 提供：

- 可注入领域 Module 的 `outbox`；
- 串行且可等待的 `flush()`；
- facts 查询与五种确定性投影；
-供 profile 和 weekly report 使用的只读 fact source。

事件注册、历史事件重放、pending outbox 首次 flush 仍由该 Module 内部完成。

### 7.3 ProfileRuntime

拥有 Evidence Repository、AI extractor、aggregator、reasoning behavior、reasoning evidence projector、global profile、portrait Module 及全部相关 barrier。

Interface 提供：

- `checkpointSink.capture(input)`，保持当前异步排队与错误记忆语义；
- 教学个性化只读查询；
- reasoning refresh/recovery；
- profile 与 portrait RouteOptions；
- course deletion 使用的 portrait refresh；
- weekly report 使用的 reasoning evidence source。

教学消息、Review 或补充学习的来源读取不进入该 Module；这些拥有原始来源的 Module 先组装当前完全相同的 checkpoint，再交给 sink。

### 7.4 CourseRuntime

拥有 CourseAuthoring Repository、Course Repository、Authoring Module、candidate coordinator、课程 facade、材料接入和 archive deletion。

Interface 提供 course authoring RouteOptions、窄 `CourseAccess` 查询、画像删除刷新入口，以及仅供现有集成测试使用的 `courseRepositories`。课程读取者不直接依赖具体 LocalFile Repository。

### 7.5 LearningRuntime

拥有 LearningSession Repository、Session Module、MessageLog、TeachingLedger、InteractiveTeaching、SupplementarySession 和教学上下文来源。

Interface 提供 learning session RouteOptions、窄 `LearningAccess`、ReviewRuntime 所需的冻结检查点/消息读取能力、ProfileRuntime 所需的来源组装能力，以及 weekly report 使用的 teaching evidence source。

教学上下文、个性化选择、暂停回复恢复和 teaching projection degraded 处理全部隐藏在此 Module。

### 7.6 PlanningRuntime

拥有 Schedule Repository、PlanFlow Repository、Planning Module 和 PlanFlow Service。Interface 提供 planning RouteOptions 与只读 schedule access。`lessonIsPlannable` 继续排除 `completed` 和 `abandoned`，锁定项、前置依赖与版本计算完全不变。

### 7.7 ReviewRuntime

拥有 Stage Review、Lesson Closure、Course Review、Review Writer、Review evidence pack、关闭事务恢复和下一课推荐协调。

该 Module 在 CourseRuntime、LearningRuntime、PlanningRuntime 全部创建后构造，因此不需要 lazy dependency 或可变占位对象。Interface 只提供 review closure RouteOptions 和 `recover()`。

教学/Review/补充学习 checkpoint 的原始来源组装可放在 LearningRuntime 内部，ReviewRuntime 仅调用其窄能力并将结果提交给 ProfileRuntime。

### 7.8 InsightsRuntime

拥有 WeeklyReportService、WeeklyReportScheduler、LearningFacts RouteOptions 以及跨 teaching/reasoning evidence 的周报附加证据装配。Interface 只提供 learning facts RouteOptions、`start()` 和 `close()`。

`close()` 必须幂等，并停止 scheduler。未来若增加其他后台 worker，也统一在此 Module 内逆序关闭，不扩展 `main.ts`。

## 8. 创建与恢复顺序

重构严格保持当前顺序：

1. 解析 DataRoot、初始化 Store layout；
2. 恢复未完成文件事务；
3. 创建 UnitOfWork 和时钟/ID 来源；
4. 创建 GenerationRuntime 并尝试恢复持久化 Provider 配置；
5. 创建 EventFactsRuntime、注册全部 event projector、重放事件并首次 flush outbox；
6. 创建 Profile、Course、Learning、Planning、Review 和 Insights Module；
7. 恢复处于 `committing` 的 lesson closure；
8. 启动 WeeklyReportScheduler；
9. 恢复过期 generation lease；
10. 按当前 fire-and-forget 语义恢复 authoring generation；
11. 恢复 interactive teaching session；
12. 刷新并投影 reasoning analysis；失败时保持 degraded readiness；
13. 汇总 `ServerDependencies` 并返回应用句柄。

关闭顺序为创建顺序的逆序。目前唯一长期后台资源是 WeeklyReportScheduler；`LocalApplication.close()` 先停止它，再返回。任何启动阶段失败只能关闭已经成功创建的资源，且重新抛出原错误。

## 9. HTTP 适配规则

- 每个内部 Module 直接产生其负责的 RouteOptions，不在 assembly 中重新实现 handler。
- RouteOptions 的字段名、函数参数、返回值和异常保持当前实现。
- `serverDependencies` 只做浅合并，允许的顶层字段与 `ServerDependencies` 完全一致。
- 路由仍只依赖 Module Interface；不得让 HTTP 层读取新的 Repository 或内部 context。
- `getRuntimeReadiness()` 汇总 Generation、Profile/Teaching 和 Store 状态，但不得触发新的恢复或副作用。

## 10. 并发、错误与生命周期

- `outboxBarrier`、`profileEvidenceBarrier` 和 `evidenceBarrier` 继续在各自 owning Module 内串行化。
- barrier 的 catch/记忆/再次抛出方式保持不变，避免把后台失败改成同步 HTTP 失败，或反向吞掉原本会阻断的错误。
- `runtimeProviderStatus` 与 `teachingProjectionStatus` 的 ready/degraded 判定保持原样。
- Repository version conflict、resource not found、lesson not completable 等错误不重新包装。
- scheduler、generation recovery 和 teaching recovery 的启动时机不调整。
- 所有新 `close()` 均幂等，不能终止不属于自身的进程或删除持久化状态。

## 11. 验证策略

### 11.1 行为刻画

重构前先运行并记录：

- `apps/server/src/bootstrap/local-application.test.ts` 的四条端到端集成测试；
- Learning Session、Review Closure、Planning、Profile、Portrait 与 Weekly Report 相关测试；
- `tools/architecture/src/teaching-data-boundaries.test.ts`。

现有测试直接搜索 `local-application.ts` 字符串的断言必须改为搜索 owning runtime 文件；断言语义不降低。

### 11.2 结构门禁

新增架构测试，要求：

- `local-application.ts` 不超过 160 行；
- `assemble.ts` 不超过 400 行；
- 两者不得直接包含 `for await`、领域命令字面量、事件 payload 或 HTTP handler body；
- `local-application.ts` 不得直接导入 `modules/*/implementation` 或 `persistence/*`；
- `assemble.ts` 只允许导入本目录内部 runtime Module、公共合同和组合所需类型；
- 每个 RouteOptions 只由一个 owning Module 创建。

### 11.3 回归验收

完成后依次执行：

```text
pnpm --filter @learning-more/server test
pnpm --filter @learning-more/server typecheck
pnpm --filter @learning-more/server build
pnpm architecture:check
pnpm equivalence:check
pnpm format:check
pnpm lint
pnpm verify
pnpm playwright:runtime
```

验收还需比较重构前后：

- `ServerDependencies` 顶层键和每个 RouteOptions 键集合；
- 全部已注册 HTTP 路由；
- 关键端到端响应 schema、错误码与状态码；
- 相同测试时钟和输入下的事件、Artifact、Repository 状态和生成任务；
- 应用关闭后 scheduler 不再触发，重启后恢复结果不变。

## 12. 完成标准

只有同时满足以下条件才算完成：

1. `local-application.ts` 不再是复杂度集中点并满足行数/导入门禁；
2. assembly 不包含跨模块业务流程，复杂度进入有明确 Interface 的 owning Module；
3. 当前所有功能与交互合同保持不变；
4. 当前未提交的 weekly report 生命周期改动得到保留并通过测试；
5. 相关定向测试、全仓 verify、架构检查和 runtime Playwright 全部通过；
6. 工作区中与本目标无关的既有修改没有被覆盖、回退或混入本目标提交。
