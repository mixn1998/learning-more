# Learning MORE 2.0：后端架构层

## 1. 架构总览

Learning MORE 当前是本地优先、单用户、模块化单体。业务服务运行在一个 Fastify 进程内，但领域模块、运行控制、文件持久化和发布激活保持明确边界。

工作区是 pnpm monorepo：

```text
apps/web             React 产品界面
apps/server          Fastify、领域模块、任务运行时与本地持久化
apps/launcher        静态页面、本地控制面、反向代理与版本切换
apps/host            Windows 登录任务、Launcher 监督与 release 激活
packages/contracts   跨端 DTO、Zod Schema 与公共枚举
packages/ui          共享 React UI
packages/test-kit    测试基础设施
tools/architecture   依赖、数据所有权与等价性门禁
tools/cli            诊断、维护与恢复命令
tools/release        便携构建、供应链和 release 验证
tools/benchmarks     容量基准
```

系统目标不是拆成网络微服务，而是在单机进程内获得：

- 可替换 AI Provider；
- 可恢复任务与文件事务；
- 可重建事实和投影；
- 可验证的模块依赖；
- 旧版本可保留的安全激活。

## 2. 运行进程拓扑

默认常驻拓扑为：

```text
Windows 计划任务 “Learning MORE”
  → Host supervisor
    → Launcher 127.0.0.1:43119
      ├─ 托管 Web 静态构建
      ├─ /control/v1/* 本地控制面
      └─ /api/* 反向代理
          → Fastify Server 127.0.0.1:43120
              ├─ .learning-more-data
              └─ .learning-more-runtime
```

Host 负责登录启动、单实例租约、Launcher 监督、候选 release 构建和切换。Launcher 即使无法启动内部 Server，也尽量保留静态诊断页面和控制面。

Launcher 只终止已经验证属于当前 Learning MORE 实例的 Server。端口被未知进程占用、实例身份不匹配或 Host 身份不可信时进入阻断状态，不强行接管外部进程。

## 3. 安全激活与版本身份

### 3.1 激活事务

工作区源码变化后，Launcher 写入带 `requestId` 的激活请求；Host 是候选构建和活动 release 切换的唯一写入者。

```text
请求激活
→ 隔离目录构建候选
→ 候选 Runtime 验证
→ Supervisor 切换活动 release
→ 提交工作区 manifest
→ 新 Launcher/Server 对外提供终态
```

首次构建失败会清理当前 attempt 并自动重试一次。连续失败或候选验证失败时保留旧活动 release 和用户数据。持久化终态只暴露稳定错误码、阶段、构建身份和时间，不暴露绝对路径、命令、密钥或原始堆栈。

### 3.2 三方版本验收

Server 启动 manifest 包含实例、进程、数据根、配置指纹、`buildId`、`protocolVersion` 和启动时间。最终激活成功要求：

1. Host 的 active build；
2. `/api/v1/runtime/ready` 的 Runtime build；
3. 实际静态站点 `/build-meta.json` 的 Web build；

三者 `buildId` 一致，且 Runtime/Web 协议一致。旧 Runtime 仍健康只表示旧版可用，不能覆盖 Host 已经记录的激活失败。

## 4. 服务装配

`apps/server/src/bootstrap/local-application.ts` 是稳定 facade，只导出合同并把创建委托给 `local-application/assemble.ts`。

组合根按依赖顺序创建内部 runtime：

```text
Foundation
→ Generation
→ Event / Facts
→ Profile
→ Course
→ Learning
→ Planning
→ Review
→ Insights
→ Home / Readiness / HTTP dependencies
```

`bootstrap/local-application/` 下的 runtime 文件是组合根内部深模块：

| 内部 runtime | 责任 |
| --- | --- |
| `foundation` | 数据根、Unit of Work、Artifact Store、时钟与实例身份 |
| `generation-runtime` | Provider、任务运行时、帧日志、运行中心控制 |
| `event-facts-runtime` | 事件日志、outbox 消费与事实存储 |
| `profile-runtime` | Profile Evidence、全局行为分析、画像与调度 |
| `course-runtime` | 建课、候选、大纲版本和课程仓储 |
| `learning-runtime` | 会话、教学智能体、教学观察、账本与学习路由 |
| `planning-runtime` | 排期与计划流 |
| `review-runtime` | 放弃/恢复、课节关闭、Review 和课程关闭 |
| `insights-runtime` | 历史投影、周报和统计查询 |
| `home-runtime` | 主页聚合视图 |

这些文件不是新的公共领域 API。跨域调用仍必须依赖各业务模块的 `interface.ts`。

## 5. 领域模块边界

业务模块位于 `apps/server/src/modules`。架构检查要求模块之间只能导入对方 `interface.ts`；禁止跨模块读取 `implementation`、`model` 或 `ports`。

| 模块 | 当前责任 |
| --- | --- |
| `course-authoring` | 大纲创建会话、材料、候选生成、确认建课、大纲修订、课程关闭与删除 |
| `generation-runtime` | 任务、调度、租约、Provider 执行、fallback、取消、超时和帧日志 |
| `interactive-teaching` | 教学 Agent、隐藏指令、教学账本、教学观察与检查点 |
| `learning-session` | 原始/补充会话、写入权、消息、暂停/恢复、计时和任务归属 |
| `review-closure` | 放弃/恢复、阶段 Review、最终 Review、课节与课程关闭事务 |
| `planning` | 单课节排期与确定性计划流 |
| `learning-facts` | 事件转事实、历史/统计/日历/周投影与周报输入 |
| `global-user-profile` | 思维行为 Episode、会话维度分析和跨会话语义归并 |
| `profile-evidence` | 受控候选证据、检查点、全局指标与画像证据投影 |
| `learning-portrait` | 证据打包、输入 manifest、画像生成、校验和版本指针 |
| `next-lesson` | 合格课节过滤、AI 推荐验证和确定性 fallback |

## 6. 课程创建数据流

### 6.1 会话与回复

大纲创建会话保存用户消息、AI 回复、材料、资源版本和候选指针。追加消息时：

1. `course-authoring` 验证状态、版本和幂等键；
2. 建课对话 Agent 提交 `course-authoring-conversation` 任务；
3. 完成回复写入会话；
4. 即使已有候选，也不自动启动候选生成。

### 6.2 显式候选生成

用户点击“生成新候选”后才提交 `RequestCandidateGeneration`：

- 新课程候选读取完整对话、当前候选和材料；
- 正式课程调整先用 `outline-candidate-alignment` 规划修改目标，再提交 `outline-candidate`；
- 同一会话只允许一个活动候选任务；
- 生成帧由 SSE 暴露；
- 任务完成后编译 Markdown、校验候选合同，并推进会话的最新候选指针；
- 取消和失败保留历史对话及上一有效候选。

确认候选通过单个事务创建正式课程、确认版大纲和课节。正式大纲修订生成新版本并维护稳定课节关系，不覆盖旧版本。

## 7. 正式教学架构

### 7.1 教学智能体输出协议

教学 Agent 的 `interactive-teaching` 任务返回两个明确分隔的区块：

```text
<learning-more-control>{完整教学状态 JSON}</learning-more-control>
<learning-more-reply>{用户可见 Markdown}</learning-more-reply>
```

控制区包含：

- `lessonPhase`；
- 当前知识点；
- 每个知识点的 `pending / learning / completed / skipped`；
- 知识点互动状态；
- 综合检测状态；
- 讨论答疑确认状态；
- 最终总结状态。

服务端使用严格 Schema 解析，并拒绝知识点集合变化、完成节点倒退、阶段倒退、未处理完知识点就进入综合检测、未经过讨论答疑就进入总结等非法指令。

### 7.2 回复、账本和观察的顺序

当前真实顺序是：

```text
提交教学任务
→ Provider 完成回复与隐藏指令
→ 提交 Assistant 消息
→ 校验并应用隐藏指令到教学账本
→ 生成任务完成帧
→ 异步进入教学观察队列
```

因此教学输出和教学观察不是同时抢占同一轮主提交：用户可见回复和账本指令先完成，观察随后异步执行。

教学账本是前端进度和课程闭环的唯一教学控制来源。教学智能体拥有进入下一阶段的判断权，确定性 reducer 只校验状态合法性和不可回退约束。

教学观察使用 `interactive-teaching-observation` 任务，每轮都读取完整学习会话历史并重建当前行为记录。它负责：

- 学习者回答、提问、推理、纠偏与跳过；
- 关键互动提示、回应和跳过；
- 未解决问题和来源消息；
- Reasoning Episode 与后续 Review/事实输入。

观察不判断检测是否通过，不决定知识点完成、教学阶段或课程闭环。观察失败会把观察状态标记为待恢复，但不会撤销已提交的 AI 回复和教学指令。

### 7.3 暂停、迟到回复与计时

`learning-session` 管理会话状态和任务归属：

- 新用户消息只允许写入 active 会话；
- 已启动任务可在会话变为 paused 后继续；
- Assistant 提交必须匹配 `sessionId`、`taskId` 和写入租约 owner；
- 身份不匹配的迟到任务不可写入；
- AI 等待、页面后台、暂停和失去写入权会关闭计时间隔；
- 服务重启时开放计时间隔按最后心跳截断。

## 8. Review 与关闭事务

### 8.1 教学检查点

在有证据的放弃或最终结束前，`interactive-teaching` 冻结 `TeachingCheckpointSnapshot`，包含：

- 教学账本状态；
- 观察完整性；
- 观察引用与来源消息；
- 来源快照哈希；
- 保留或丢弃决策。

`review-closure` 只消费冻结且满足完整性条件的检查点，不读取浏览器当前显示状态。

### 8.2 课节关闭

课节关闭是可恢复事务：

```text
持久化结束意图
→ 停止计时并冻结会话
→ 冻结教学检查点
→ 生成阶段或最终 Review
→ 校验来源与内容
→ 原子提交 Review
→ 最终 Review 成功后提交课节完成事实
```

失败时保留原会话和已有阶段 Review，并允许重试或恢复学习。内部可以出现 `closing` 处理态，但不新增用户可见课节生命周期。

### 8.3 Review 不可变性

- 同一课节始终使用稳定 `reviewId`；
- 阶段 Review 可被后续阶段 Review 原子覆盖；
- 最终课时 Review 成功后不可修改；
- 课程总 Review 成功后不可修改；
- 补充学习不反向修改原始会话和 Review。

## 9. 行为、事实、档案与画像数据链

### 9.1 学习事实

领域事务通过 outbox 发布 `LearningEventEnvelope`。`learning-facts` 只接受允许的已提交事件；生成 delta、前端遥测、Provider 错误和中间 AI 状态不会成为学习事实。

事实投影包括：

- history；
- course summary；
- statistics；
- calendar；
- weekly。

投影保存 checkpoint，可增量执行或全量重建。课程永久删除通过撤销事件使重放后的投影不再包含该课程贡献。

### 9.2 原始行为与会话聚合

教学观察中的有效推理行为进入 `ReasoningBehaviorEpisode`，保留自由语义摘要、会话/课程/课节上下文和精确来源引用。暂停学习事实在入口处排除。

阶段或最终 Review 成功后，Profile Runtime 冻结该 Review 与同一会话的 active Episode，形成受控检查点，再提取“学习会话 + 抽象维度”的会话聚合。最终 Review 会取代同一会话的阶段聚合，不增加独立来源数。

课程总 Review 可以消费同主题会话聚合形成主题成果，但不把课程 Review 自己重新登记为画像证据。

### 9.3 全局用户档案

`global-user-profile` 对不同学习会话的抽象维度进行第二次语义归并，解决“措辞不同、行为本质一致”的问题。独立来源按真实 `sessionId` 计算；单一会话只能形成暂定模式。

至少两个真正独立学习会话支持的稳定维度，才会：

- 投影为画像可消费证据；
- 进入教学个性化隐式上下文；
- 出现在用户可见学习画像的候选输入中。

### 9.4 学习画像

`profile-evidence` 同时管理结构化学习事实候选和全局行为维度投影，并按状态、来源独立性、复合支持和预算筛选。`learning-portrait` 将允许的证据打包为不可变 input manifest，提交 `learning-portrait` 任务并校验所有引用。

思维行为证据按“动态全局维度 + 独立学习会话”投影，但其用户可读摘要保留该会话所引用 Episode 的具体 `behaviorSummary`，不能重复保存全局维度定义。兼容读取旧证据时，服务端依据 `sourceGroupId` 和 `sourceRefs` 从有效 Episode 恢复具体摘要；该过程是纯读投影，不改写画像版本，也不触发 AI 任务。

只有成功版本推进 current cursor；失败版本保留审计信息但不替换上一成功画像。学习画像是展示产物，不反向写入全局用户档案。

画像读取与画像刷新是不同的命令边界。`GET` 当前画像和证据只读取已持久化快照，不恢复 Review、不同步全局档案，也不提交 AI 任务。证据同步、全局行为分析和画像生成只在刷新协调器内部执行，因此页面导航不能产生画像写入副作用。

## 10. 周报、画像与后台调度

周报按 `Asia/Shanghai` 的完整周边界冻结事实、教学账本和行为证据。成功产物不可变；失败状态可读，但当前没有公开手动重试 HTTP 命令。

画像按 `Asia/Shanghai` 每周六 00:00 触发后台刷新；手动刷新和定时刷新经过同一串行协调器。普通启动和页面读取只布置或消费既有快照，不用真实 AI 画像生成阻塞 Server readiness，也不会因为用户切换到画像页而刷新。

## 11. AI 生成运行时

### 11.1 任务模型

AI 能力通过 `GenerationRuntime`/`GenerationExecution` 提交统一任务。请求包含：

- 稳定任务键与输入快照哈希；
- `taskKind`；
- `interactive` 或 `background` 任务组；
- owner；
- Provider、模型、fallback 和最大尝试次数；
- 优先级与完整 prompt。

相同任务键和快照会 join 同一非失败任务。提交时把当前 Provider 和模型配置快照到任务；运行中心后续切换只影响新任务。

任务状态为 `queued / running / completed / failed / cancelled / timeout`。运行租约过期后，未产生输出的任务可重新入队；已有部分交互输出的任务保留为可恢复中断，不静默换 Provider 重写。

### 11.2 当前生产场景

场景注册表当前只包含有生产提交路径的名称：

| 场景 | 用途 |
| --- | --- |
| `course-authoring-conversation` | 建课与大纲调整对话 |
| `outline-candidate` | 完整候选大纲 |
| `outline-candidate-alignment` | 正式大纲调整目标规划 |
| `interactive-teaching` | 教学开场与回合 |
| `interactive-teaching-observation` | 完整历史教学观察 |
| `stage-review` | 阶段 Review |
| `final-review` | 最终课时 Review |
| `course-review` | 课程总 Review |
| `weekly-report` | 周报 |
| `learning-portrait` | 学习画像 |
| `next-lesson-recommendation` | 下一课语义推荐 |
| `reasoning-behavior-analysis` | 跨会话行为维度分析 |
| `profile-evidence-extraction` | 受控画像证据提取 |

注册表不包含计划流或“是否生成候选”的意图判断场景：计划流由确定性程序实现，候选是否生成由用户按钮决定。

### 11.3 调度与 fallback

调度考虑 Provider `maxConcurrency`、任务组、owner、优先级和提交顺序。默认 fallback 顺序来自 `LEARNING_MORE_FALLBACK_PROVIDER_IDS`，最大尝试次数来自 `LEARNING_MORE_FALLBACK_MAX_ATTEMPTS`。

fallback 只在错误可重试且尚未产生首个内容 delta 时发生；输出一旦开始，系统不会切换 Provider 拼接同一回复。

`GenerationFrameLog` 为每个任务保存递增序号的状态和内容帧。SSE 客户端按序号续读；服务重启后，业务模块读取任务、帧、owner 和领域状态恢复提交。

## 12. Provider 接入

### 12.1 Mock

Mock 始终创建，提供确定性脚本和故障注入，主要用于开发、测试和无外部 AI 环境。

### 12.2 OpenAI-compatible API

只有配置 Base URL 和模型时才加入 Provider 列表。当前实现调用兼容的流式 `/chat/completions`，并使用 `/models` 做健康检查。请求主要传递：

- `model`；
- 单条 user message 中的完整 prompt；
- `stream: true`；
- 可选 Bearer API Key。

当前没有通用 temperature、top-p、max-tokens 等运行中心参数面板。

### 12.3 Codex CLI

Codex CLI 按显式路径、PATH 和当前用户安装目录发现可执行文件，并执行：

1. `codex --version`；
2. `codex login status`；
3. `codex debug models`。

运行中心只展示 CLI 标记为可列出的模型及其支持推理强度。生成使用非 shell 子进程、只读 sandbox、临时会话、显式模型和 `model_reasoning_effort`。模型目录是动态运行数据，不在代码中固定为两个选项。

### 12.4 切换与重连

Provider 切换经过：公开配置/密钥句柄验证、切换前健康检查、运行时切换、切换后健康检查和配置原子保存。失败时尝试恢复上一 Provider 与配置。

重连重新应用持久化配置并执行真实健康检查，不只是刷新前端状态标签。

## 13. HTTP 边界

HTTP 路由按业务域注册：

| 路由域 | 主要资源 |
| --- | --- |
| readiness / home | Runtime readiness、主页聚合 |
| course authoring | 大纲会话、消息、材料、候选任务、确认、大纲版本、课程 |
| generation | 生成任务 SSE |
| learning sessions | 课节状态、原始/补充会话、开场、消息、暂停/恢复、停止生成 |
| review closure | 放弃、恢复、课节关闭事务、课程关闭与课程 Review |
| planning | 排期项、计划流预览、确认和管理 |
| learning facts | 历史、课程摘要、统计、日历、周视图与周报 |
| profile / portrait | 档案事实、行为分析、画像证据、画像刷新与版本 |
| runtime control | Provider 目录、登录、状态、切换、重连和诊断 |

业务写命令使用幂等键、资源版本和统一 `ApplicationProblem`。SSE 只传递生成帧；领域状态提交始终发生在服务端模块内。

## 14. 文件持久化

主要数据区包括：

## 15. 启动恢复顺序

当前启动恢复刻意分为阻塞和后台两部分：

1. 恢复 Store 事务并创建模块；
2. 修复大纲活动引用；
3. 恢复正在提交的课节关闭事务；
4. 启动 Insights/周报调度；
5. 恢复过期生成租约；
6. 后台恢复候选任务；
7. 后台按完整历史恢复教学观察；
8. readiness 对外可用后，再后台恢复 Profile 检查点和全局行为分析。

教学观察恢复与课程创建没有业务依赖，只是共享同一服务启动过程；因此它被放入后台，历史会话恢复失败不应阻塞新大纲生成或 Host 的候选版本健康窗口。

## 16. 本地安全

- Server 与 Launcher 默认只监听 `127.0.0.1`；
- Server 写请求校验 Origin 与 CSRF；
- Launcher 控制写入要求短期 capability；
- Windows 密钥使用当前用户 DPAPI Secret Store；
- Provider 配置只保存公开字段和密钥句柄；
- 诊断输出进行脱敏；
- Web/Runtime 构建不一致时前端禁止写入。

## 17. 当前运行状态与限制

本次核验时活动 Runtime、Store、投影和 Provider 均为 ready，活动构建与当前主线一致；当前选择的是健康的 Codex CLI Provider。

明确的架构限制：

- Runtime 配置 Schema 有 `interactiveConcurrency` 和 `backgroundConcurrency`，但当前组合根没有把它们传给 `createGenerationRuntime`；实际并发由 Provider、任务组、owner 和调度顺序控制。
- API Provider 的模型参数面仍较窄。
- 周报失败状态没有公开手动重试路由。
- Profile/画像恢复链较长，已通过后台化避免阻塞 readiness，但其最终可用性仍依赖 Review 检查点、行为分析、证据投影和画像生成依次成功。
- 动态模型目录、Provider 健康和活动 release 均属于运行数据，文档不把本次采样值写成永久架构常量。
