# Learning MORE 2.0：后端架构层

## 1. 架构结论

后端是 Node.js + TypeScript 模块化单体。领域能力在同一进程内组合，通过小而深的模块接口隐藏状态机、幂等、事务、投影和恢复细节；内部事件分发保持单一实现，不引入远程事件总线。

两类变化方向已经通过 seam 隔离：

- Repository：当前 LocalFile Adapter，未来可替换数据库 adapter。
- AI Provider：当前支持多个 Provider 和运行时切换，业务模块不绑定厂商协议。

## 2. Monorepo 结构

```text
apps/
  web/                 React + Vite 前端
  server/              模块化后端与 HTTP API
  launcher/            本地控制面、静态站点和 Server 进程监督
  host/                Windows 独立守护与版本激活协调
packages/
  contracts/           Zod 合同、错误码、OpenAPI、流协议
  domain/              可复用领域值对象与规则
  infrastructure/      本地文件、事务、锁、事件与读模型基础设施
tools/
  cli/                 诊断、迁移、备份、恢复等维护命令
  release/             便携构建、发布演练与供应链检查
tests/
  recovery/            跨进程、激活与故障矩阵
docs/
  架构方案/             长期有效的架构决策
  项目2.0现状/          当前实现与产品事实
```

共享包不得反向依赖应用；领域模块不得直接引用 React、Launcher 或具体 AI SDK。

## 3. 领域模块

### 3.1 CourseAuthoring

负责课程创建对话、候选大纲、版本确认与修订。对外只暴露创建/继续对话、生成候选、确认、修订、读取版本和删除课程等用例。

内部隐藏：

- 候选与正式版本状态。
- 已完成课时锚点对齐。
- 过去对话压缩与完成课时概要上下文。
- 明确重复自动去除、模糊重复待确认。
- 历史版本只读和当前版本切换。

### 3.2 LearningSession

拥有课时会话生命周期、租约、暂停、恢复、放弃、时间累计和正式/补充会话边界。它判断某课时能否开始或继续，但不负责生成教学内容。

### 3.3 InteractiveTeaching

负责教学阶段状态机、消息修订、流式响应、隐藏指令、教学观察、回复优先持久化和恢复对账。

状态推进由确定性 reducer 执行；AI 只能提出符合 schema 的状态指令，不能直接写终态。关闭相关的 `phase + closureInquiry + summaryStatus` 必须通过允许组合校验。

### 3.4 ReviewClosure

负责阶段 Review、最终 Review、课程 Review 和可恢复关闭事务。它把生成任务、Review 文档提交、会话终态和下游事实写入一个可对账流程。

前端精简 Review 只是一层纯投影，完整 Review 和证据引用仍由本模块保存。

### 3.5 Planning 与 NextLesson

Planning 从当前大纲、学习状态和计划事实推导可安排集合，排除 completed 与 abandoned，并提供幂等安排命令。NextLesson 基于相同边界提供推荐和解释，但不拥有计划事实。

### 3.6 LearningFacts

把领域事件投影为规范化学习事实、统计序列、周窗口和来源修订。事实是画像与统计的共同底座，不直接保存用户画像结论。

### 3.7 GlobalUserProfile

维护跨课程的语义学习档案：用户明确偏好、重复出现的稳定学习行为、来源快照和面向教学的压缩摘要。稳定行为通常至少需要两个独立会话；明确偏好可直接进入稳定集合。

### 3.8 ProfileEvidence

负责原始行为片段、会话聚合维度、候选证据、来源组去重、正反证据检查和跨会话推理分析。原始 reasoning episode 不能绕过会话层直接进入画像。

### 3.9 LearningPortrait

负责画像输入冻结、后台生成、手动/定时刷新、版本保存和当前静态快照切换。正式画像声明必须引用证据，并携带置信说明、限制和反向证据检查结果。

### 3.10 GenerationRuntime

为所有 AI 场景提供统一任务语义：幂等键、队列、租约、并发、Provider 路由、推理强度、token 预算、流、停止、重试和结果保留。

## 4. 应用装配顺序

本地应用按依赖顺序装配：基础设施 → Generation Runtime → 事件与事实 → 全局档案 → 课程 → 完成课时引用对账 → 学习 → 规划 → Review → 关闭恢复 → 洞察与画像。

启动阶段还会：

- 恢复处于 committing 的关闭事务。
- 回收过期生成租约。
- 恢复课程、教学和 Review 相关后台任务。
- 启动周报与画像调度。
- 检查关键投影是否可用。

readiness 只有在存储、Provider 与必要投影满足条件时才报告可服务；非关键后台投影失败可以进入 degraded，并由恢复任务继续处理。

## 5. 合同体系

### 5.1 命令

命令使用明确动词和业务标识，例如创建课程、确认大纲、开始会话、提交消息、安排课时、刷新画像。合同至少包含：

- `requestId` 或 `idempotencyKey`。
- 目标 aggregate/session/version 标识。
- 乐观并发所需版本（如适用）。
- 业务载荷。

成功响应返回领域结果和新的版本/修订信息；重试同一幂等键必须返回同一业务结果或明确冲突。

### 5.2 查询

查询返回面向页面的读模型，不暴露 Repository 文件路径。列表使用游标或分页；组合查询带修订号、生成时间和 ETag。

### 5.3 事件

领域事件使用稳定名称、aggregateId、eventId、occurredAt、schemaVersion 和业务 payload。事件先与聚合写入同一事务单元，再触发事实和读模型投影。

内部事件分发当前为进程内实现；模块依赖事件合同，而不是一个预设的分布式总线接口。

### 5.4 错误

共享错误合同区分：

- 验证失败。
- 资源不存在或已归档。
- 生命周期冲突。
- 乐观并发冲突。
- 幂等冲突。
- 生成进行中、已停止、不可重试或 Provider 不可用。
- 投影暂不可用和运行时未就绪。

HTTP 响应只暴露安全的错误码、消息和可选恢复动作；诊断详情写入本地日志。

## 6. HTTP 与流式协议

控制面由 Launcher 在 `127.0.0.1:43119` 提供，应用 API 由 Server 在 `127.0.0.1:43120` 提供。浏览器通常通过 `43119` 的同源入口访问静态前端和代理 API。

普通 API 采用 JSON。命令使用 POST/PATCH/DELETE，查询使用 GET，并严格按共享 Zod schema 解析。

流式生成采用可增量解析的帧协议，帧类型至少覆盖：

- 文本增量。
- 可选工具或阶段元信息。
- 成功终止。
- 用户停止。
- 失败终止。

每条流与 generation task、message revision 和幂等键关联。网络连接结束不等于任务失败；客户端可查询任务状态并恢复最终结果。

## 7. 本地文件数据架构

### 7.1 数据类别

DataRoot 下按职责保存：

- 聚合 JSON：课程、版本、会话、计划、任务、画像版本等结构化状态。
- Markdown：大纲、教学内容、Review、周报等可读产物。
- 事件与事实：追加式业务记录及规范化事实。
- 读模型：首页、历史、统计、日历、档案、证据和画像输入。
- 索引：业务 ID 到文件/版本/关联的定位信息。
- 事务日志：Unit of Work、提交阶段和恢复标记。
- 运行元数据：构建、迁移、锁、备份和健康信息。

### 7.2 写入规则

所有关键写入遵守：

1. 在临时文件中写完整内容。
2. 校验 schema 与内容校验和。
3. 原子替换目标文件。
4. 更新索引和来源修订。
5. 提交事务阶段标记。

跨文件写入由 Unit of Work 记录意图和阶段；进程中断后根据日志继续提交或回滚到前一完整状态。Store write lease 避免两个 Server 同时写同一 DataRoot。

### 7.3 schema 与迁移

每个持久化 JSON 保存 `schemaVersion`；Markdown 由相邻元数据或合同版本识别。迁移是显式、可备份、可重复运行的维护动作：

- 启动前识别版本。
- 先生成备份或恢复点。
- 在临时目标执行迁移并校验。
- 原子切换。
- 失败则保持旧数据不变。

运行时代码不长期维护“新旧字段都猜一下”的无界兼容逻辑。

## 8. 投影与一致性

### 8.1 来源修订

当前读源至少划分为 `catalog`、`learning`、`schedule`、`facts`、`weekly`。事务提交时只递增受影响的 scope。

首页快照以 catalog + learning + schedule 修订组合为身份。修订未变且 checksum/schema 有效时，直接从内存或磁盘返回快照；变化时才重建并原子替换。

### 8.2 重建

读模型可从聚合、事件或规范化事实重建。重建流程：冻结输入水位 → 在临时目录投影 → 校验计数、引用和 checksum → 原子发布 → 更新水位。

投影异常不会反向修改源聚合。若旧快照仍有效，查询可继续提供旧值并标记 stale/degraded；若不可安全提供，则返回明确暂不可用。

### 8.3 删除一致性

课程永久删除以事务清单定位全部下游引用。源数据删除成功后，相关修订递增，统计、档案与候选证据失效并重建。学习笔记保存创建时的学科、课程和课节元数据快照，不随源课程删除。

## 9. AI 任务架构

### 9.1 已登记场景

当前 15 个场景为：课程创建对话、候选大纲、候选大纲对齐、教学权重分析、交互教学、教学观察、补充学习、阶段 Review、最终 Review、课程 Review、周报、下一课推荐、推理行为分析、语义学习档案、档案证据提炼。

每个场景配置输入/输出合同、默认推理强度、并发策略、预算和可恢复性。高复杂度大纲候选使用较高推理强度；周报和下一课推荐倾向低强度；教学按实际轮次动态选择。

### 9.2 调度与并发

- 同一业务幂等键只产生一个逻辑任务。
- 场景可设置全局与资源级并发槽。
- 长任务领取有过期租约，崩溃后可重新领取。
- 停止是持久化意图；Provider 返回后仍要检查停止状态。
- 失败保留已确认的流内容和错误终态，并依据场景规则决定是否允许重试。

### 9.3 Provider Adapter

Provider 接口只暴露生成所需的消息、工具、结构化输出、流和取消能力。具体认证、URL、模型名、错误映射与 SDK 适配留在 adapter 内。

运行时切换 Provider 不迁移正在执行的任务；新任务读取最新配置，旧任务按原快照完成或失败。密钥只从受保护配置或环境读取，不进入前端、日志、任务 payload 或备份明文清单。

## 10. 学习档案与证据管线

```text
领域事件/Review/对话
  → 规范化学习事实
  → 原始行为片段
  → 会话聚合维度（reasoning-session-dimension@2）
  → 候选证据与来源组去重
  → 跨会话分析（reasoning-global-analyzer@2）
  → 语义学习档案
```

关键治理规则：

- `reasoning-evidence@1` 不再作为画像输入。
- 单次行为只在本次会话范围内解释。
- 稳定观察通常需要至少两个独立 session/source group。
- 同一原始来源的多个投影不算多个独立证据。
- 候选证据记录 polarity、strength、dependencies、refs、governance 和 status。
- 当前版本停止画像生成和教学个性化消费，但保留上述上游档案生产链。

## 11. 周期任务

- 周报：面向已经结束的周窗口生成；启动时对账遗漏，失败后延迟重试。
- 任务生成新产物后先校验，再原子切换“当前版本”；旧静态产物保持可读直到替换成功。

## 12. 本地运行与自愈

### 12.1 进程链

```text
Windows Task Scheduler
  → Host（单实例、独立于 Codex/终端）
    → Launcher（43119，控制面 + 静态前端 + API 代理）
      → Server（43120，应用 API）
```

任务调度器在用户登录时触发 Host，不采用每分钟重复启动。Host 用租约确认单实例并监督 Launcher；Launcher 对 Server 的普通意外退出执行退避重启，并用重启风暴保护避免无限高频拉起。

交互包装器负责需要时打开主页，后台守护链不主动反复打开浏览器。

### 12.2 工作区构建与激活

Host 观察源码身份变化后，请求 Launcher 构建候选版本。候选版本依次经历构建、合同/健康验证、激活和 readiness 校验；失败则保持或回滚到前一健康版本。

控制面同时校验 active build、served web build 和 Server readiness build，避免“网页是新版、API 是旧版”的混合状态。

### 12.3 密钥与诊断

- 密钥不写入仓库和普通日志。
- 公开状态接口只返回安全错误码和阶段。
- 详细日志、本地 PID/租约、激活记录和崩溃原因保存在受控运行目录。
- 诊断命令读取状态，不通过启动额外永久进程来掩盖守护链问题。

## 13. 测试、构建与发布

测试按反馈速度分层：

1. **日常快速层**：改动相关单元/模块测试、类型检查和格式检查。
2. **模块合同层**：共享 schema、HTTP、流协议、Repository 和 Provider adapter。
3. **集成层**：真实本地文件、事务、投影、关闭和任务恢复。
4. **端到端层**：关键用户闭环和功能等价断言。
5. **恢复/发布层**：进程崩溃、构建激活、回滚、备份恢复和故障矩阵。

CI 使用受控 worker 数，避免 Windows 文件和进程类测试互相争用。便携发布先执行验证、构建 release artifact，再做发布演练与供应链检查。

日常开发不应每次运行完整恢复矩阵；合并或发布前才运行全量、恢复和发布演练。

## 14. 备份与损坏恢复

备份以 DataRoot 一致性快照为单位，包含聚合、Markdown、事件、索引、读模型版本和迁移元数据；可重建缓存可以选择不纳入长期备份，但必须记录重建版本。

恢复顺序：停止写入 → 校验备份清单/checksum → 恢复到临时目录 → 运行 schema/引用审计 → 重建可重建读模型 → 原子切换 DataRoot → readiness 验证。

若只有读模型损坏，从源聚合/事实重建；若聚合损坏，必须恢复备份，不能依赖画像或统计反推业务事实。
