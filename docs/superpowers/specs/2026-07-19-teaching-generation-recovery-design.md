# 正式课程教学生成可靠恢复设计

## 目标

彻底消除正式课程中以下同源故障：

- AI 任务已经完成，但回复没有写入学习会话；
- 点击“重新生成”后任务永久停留在 `queued`，页面持续显示“正在思考中”；
- 服务激活、页面暂停、资源版本变化或事件流断开后，任务、会话和页面状态彼此不一致；
- 用户编辑、停止或发送新内容后，旧任务仍可能回写过期回复；
- 技术中断后只能重复输入，无法恢复同一次未完成回复。

最终不变量是：每个已发送用户回合最多提交一条完整 AI 回复；只要任务身份仍匹配，该回复可以跨暂停和服务重启完成；一旦身份失配，旧任务必须终止且永不回写。

## 已确认产品语义

- 页面进入后台或学习会话暂停，只暂停计时和新输入。
- 已经启动的 AI 回复在身份与任务匹配时继续生成并完整写入。
- 用户此前已经发送内容但尚未得到回复时，暂停状态下允许“重新生成”；该操作不恢复计时，也不开放新输入。
- 用户主动停止、重新编辑或以新消息替换当前回合后，旧生成任务失效。
- 重新生成恢复的是同一未回答回合，不新增重复用户消息，也不替换已完成历史消息。

## 故障证据与根因

### 跨版本丢失回复

`task_f051d514-741a-4c99-bf30-cc0750152975` 于 2026-07-19 18:19 创建。服务在 18:31 激活 `192f31a` 并重启；任务于 18:32 完成，产出了合法的控制区和回复区，但学习会话没有对应助手消息。

当前恢复只以 `session.activeGenerationTaskId` 为入口。一旦这个引用在重启、停止或前端收敛过程中先被清除，已完成任务便失去业务归属，无法补交回复。

### 孤儿排队任务

`task_a3545012-63ce-4de6-9838-ec775a73bcae` 已持久化为 `queued`，但没有执行尝试、事件日志或 Provider 进程；会话同时处于 `paused` 且没有活动任务引用。

当前流程先调用生成运行时 `submit`，再执行 `StartSessionGeneration`。后一步遇到暂停状态、写租约或资源版本冲突时，前一步写入的任务不会自动取消；相同输入的幂等提交又会持续返回同一个孤儿任务。

### 页面无限等待

前端在请求开始时先进入本地 `generating` 状态。它主要依赖事件流结束来收敛，而孤儿任务没有事件日志，也不会进入终态，因此页面没有权威信号退出“正在思考中”。

## 方案比较

### 方案一：失败分支补取消

在 `StartSessionGeneration` 失败时取消刚提交的任务。改动最小，但进程恰好在任务提交后崩溃时仍会留下孤儿，也无法找回已经完成但未提交的回复。

### 方案二：生成任务和学习会话共用事务

把两个聚合写入同一事务可以消除部分双写窗口，但会让通用 Generation Runtime 依赖学习会话领域，并且 Provider 完成、消息提交和教学指令应用仍然存在跨事务窗口。

### 方案三：持久化身份 + 可恢复 Saga

保留两个模块边界，把每个生成任务视为持久化业务尝试，记录明确的来源回合，并由教学协调器对所有中间状态进行补偿或恢复。该方案不能让跨模块操作在物理上瞬间原子，但能保证每个崩溃窗口都确定性收敛，是本次采用方案。

## 架构设计

### 1. 生成任务携带业务请求引用

Generation Request 与 Generation Task 增加可选的通用 `requestRef`。通用运行时不解释该字段，只负责原样持久化。

正式课程中：

- 普通教学和重新生成使用来源用户消息 ID；
- AI 教学开场使用稳定引用 `opening:<sessionId>`；
- `ownerRef` 继续保存学习会话 ID；
- `inputSnapshotHash` 继续标识完整生成上下文。

因此服务重启后无需依赖内存 Map，也能回答“这个任务属于哪个会话、正在回答哪个回合”。

### 2. 教学生成协调器成为唯一生命周期入口

`InteractiveTeaching` 内部新增或提取一个深模块式协调器，统一承担：

1. 校验课程、课节、会话、写入权和来源消息身份；
2. 准备并提交幂等生成任务；
3. 将任务绑定到学习会话；
4. 在返回 HTTP 202 前建立可读取的任务事件日志；
5. 启动 Provider 执行；
6. 验证控制指令，保存回复制品并提交助手消息；
7. 应用教学账本指令；
8. 终结任务事件并排队教学观察；
9. 在任何正常异常路径中执行补偿。

控制器和前端不能分别拼装这套流程。

### 3. 正常请求的提交顺序与补偿

正常流程保持“任务先提交、会话后绑定”，因为任务 ID 由 Generation Runtime 产生；但补齐确定性补偿：

1. 读取并校验最新会话和来源消息；
2. 提交带 `requestRef` 的 `queued` 任务；
3. 重新读取会话最新版本，避免使用上下文组装前的陈旧版本；
4. 将任务绑定会话；重试/恢复允许在 `paused` 状态绑定，但不改变暂停状态；
5. 建立事件日志；
6. 返回已接受响应并异步执行。

步骤 3 至 5 任一步在进程仍存活时失败，协调器必须：

- 将任务取消为终态；
- 若会话已经绑定则清除绑定；
- 若事件日志已存在则发出终态事件；
- 向客户端返回可识别错误，而不是留下永不执行的任务。

进程在任意两步之间崩溃时，由恢复扫描处理。

### 4. 暂停状态与生成状态正交

学习会话的 `active/paused` 继续只控制计时和新用户输入。生成绑定不再隐含要求会话必须 `active`：

- 新用户消息只能在 `active` 状态追加；
- 对已存在且仍未回答的消息执行 retry/recovery，可以在 `paused` 状态绑定生成任务；
- 绑定、生成和提交助手消息均不得自动恢复计时；
- 回到前台后的自动恢复仍只由原有页面生命周期控制。

领域命令必须显式区分普通新回合与 `retry/recovery`，禁止用一个无语义布尔值绕过所有状态校验。

### 5. 确定性恢复扫描

恢复器同时读取学习会话和该会话所属的 `interactive-teaching` 任务，不再只读取 `activeGenerationTaskId`。

按以下矩阵收敛：

| 任务状态 | 会话绑定 | 来源消息仍是未回答尾回合 | 处理 |
|---|---|---|---|
| queued | 是 | 是 | 确保事件日志存在并调度执行 |
| queued | 否 | 是 | 重新绑定后调度；暂停状态保持暂停 |
| queued | 任意 | 否 | 取消并禁止回写 |
| running | 是或可安全恢复 | 是 | 接管并等待终态 |
| running | 否且身份失配 | 否 | 取消 |
| completed | 未提交助手消息 | 是 | 解析、校验并幂等补交回复和教学指令 |
| completed | 已提交相同 taskId | 任意 | 仅补齐缺失的教学指令或终态事件，不重复消息 |
| failed/cancelled/timeout | 是 | 任意 | 清除会话绑定并暴露可重试状态 |

恢复所需身份条件：

- `ownerRef` 与当前会话一致；
- `requestRef` 与尾部未回答用户消息一致；
- 消息之后没有完整助手回复；
- 该回合没有被编辑、替换、停止后发送新消息或显式废弃；
- 课程、课节和会话绑定身份一致。

任一条件不满足时宁可取消旧任务，不允许错写回复。

### 6. 服务激活恢复

服务启动后立即注册恢复任务，不把恢复错误静默吞掉：

- 已完成任务的补交应快速执行；
- 仍在运行的 Provider 任务由后台接管，不阻塞服务对其他页面就绪；
- 恢复状态和失败原因写入结构化运行日志；
- 同一会话同一时间只有一个恢复 Promise；
- 后续页面查询也触发轻量幂等核对，避免只依赖一次启动扫描。

### 7. 前端状态以服务端事实收敛

前端可以立即显示“正在思考中”，但不能永久只相信本地 reducer：

- HTTP 接受响应返回前，后端必须保证任务已绑定且事件日志可读；
- 事件流断开或在启动确认窗口内没有任何快照/事件时，前端查询会话和任务状态；
- 后端报告任务终止、失配或不存在时，退出生成态并显示重新生成按钮；
- 后端报告任务已完成且消息已经提交时，刷新消息并退出生成态；
- 后端报告仍在合法运行时，使用新的游标继续事件流；
- 页面暂停时重新生成按钮仍可使用，但输入框和计时器保持暂停。

启动确认窗口只是触发权威核对，不直接判定 AI 超时；真正运行中的长任务仍可继续。

### 8. 编辑、停止与新消息的失效规则

- 点击重新编辑时，先把当前生成尝试标记为 superseded/取消，再开放编辑状态；
- 停止生成保留已经展示的中断内容，但该任务不能再提交完整回复；
- 新消息只能在旧回合已经终结后提交；
- 恢复器发现来源消息已被替换时必须取消旧任务；
- 助手消息提交以 `generationTaskId` 幂等，重复恢复不能生成第二条消息。

## 现有数据修复

激活新版本时执行一次兼容恢复：

1. 新任务直接使用 `requestRef`；
2. 旧任务仅在能够从旧 Prompt 中确定提取来源消息 ID，且会话只有一个尾部未回答用户消息时才允许恢复；
3. 同一回合同时存在 completed 与 queued 旧任务时，优先恢复最新合法 completed 结果，并取消 queued 孤儿；
4. 多个候选、来源不明或已有后续消息时不自动提交，只取消不可执行任务并开放重新生成；
5. 修复过程不恢复计时、不新增用户消息、不覆盖历史完整助手消息。

当前已知数据应当收敛为：补交 `task_f051...` 的合法完整回复，取消 `task_a354...` 的孤儿排队任务，并保持会话暂停状态。

## 错误处理与可观测性

每个阶段记录统一字段：`sessionId`、`taskId`、`requestRef`、`inputSnapshotHash`、阶段、恢复动作和最终结果。

必须区分：

- `generation_attach_conflict`：任务无法绑定会话；
- `generation_identity_stale`：来源回合已失效；
- `generation_orphan_cancelled`：孤儿任务已取消；
- `generation_reply_recovered`：已完成回复成功补交；
- `generation_recovery_ambiguous`：旧数据无法安全判断；
- Provider 自身失败和解析失败。

日志不得包含完整 Prompt、用户原文或回复正文。

## 验证策略

### 后端故障注入测试

在以下每个边界模拟进程中断并重新创建应用实例：

1. 任务提交后、会话绑定前；
2. 会话绑定后、事件日志创建前；
3. Provider 运行中；
4. Provider completed 后、助手消息提交前；
5. 助手消息提交后、教学指令应用前；
6. 教学指令应用后、终态事件前。

每项均断言最终只有一条助手消息、没有永久 queued/running 孤儿、会话绑定正确且教学指令最多生效一次。

### 状态语义测试

- paused retry 能生成并提交回复，计时区间保持关闭；
- paused 状态仍拒绝追加新用户消息；
- 资源版本在上下文组装期间变化时重新读取并安全绑定；
- 编辑、停止和后续消息使旧任务失效；
- 同一 retry 重复请求幂等；
- 事件流断开后可以重新连接；
- 没有事件日志的任务不会让页面无限等待。

### 真实数据回归

使用当前故障任务构造去标识化固定夹具，先证明旧代码产生：

- completed 但无助手消息；
- queued、零尝试、无事件日志且无会话绑定。

修复后同一命令必须分别得到“回复已补交”和“孤儿已取消”的绿色结果。

## 完成标准

- 原始两个故障夹具均收敛；
- 所有故障注入测试通过；
- 暂停重试不恢复计时；
- 前端不再无限显示“正在思考中”；
- 服务激活期间完成的回复能够自动写入身份匹配的会话；
- 编辑或新消息后的旧回复不会回写；
- 当前真实数据恢复正常；
- 代码中不存在只依赖内存 Map 或单次 SSE 连接判断回复归属的关键路径。
