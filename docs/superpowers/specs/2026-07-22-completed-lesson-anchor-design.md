# 已完成课时跨大纲版本沿用设计

## 范围

本次只修复已完成课时在大纲修改中的身份与上下文连续性，不增加候选课语义判重、人工确认状态、全局语义门禁或新的前端工作流。

## 领域规则

1. `learning.progress = completed` 是唯一的已完成判定；存在会话、阶段 Review 或一般学习证据都不能代替完成状态。
2. 已完成课时是课程后续版本的冻结锚点。后续版本继续引用原 `lessonId` 和原 `LessonDefinition`，不复制、不改写、不重新绑定完成事实。
3. 发布新大纲时，即使模型遗漏已完成课时，服务端也必须把全部已完成锚点保留在课程的活动 `lessonIds` 中。
4. 模型若用原 `semanticKey` 返回了已完成课时，服务端采用冻结定义而不是模型改写内容。
5. 本次不对使用其他 `semanticKey` 的近义候选课做自动语义判重；通过生成上下文明确禁止重复，避免把不确定语义判断变成发布阻断。

## 大纲修改上下文

每次修改已有课程大纲时，过去版本上下文固定由两部分组成：

1. **过去版本大纲生成对话上下文的压缩**：汇总历史大纲会话中的用户目标、边界、偏好和已达成的调整结论；使用有界、确定性的摘要表示，当前调整会话仍作为当前请求单独提供。
2. **过去版本已完成课时内容的大纲概要**：逐节提供稳定 `semanticKey`、标题、学习目标和核心知识点，并明确标记 `用户已完成`。

生成约束要求模型：

- 每个已完成课时必须在候选大纲中出现且只出现一次；
- 使用提供的稳定 `semanticKey`、标题、学习目标和核心知识点；
- 把它标为用户已完成，而不是新增或待学习；
- 后续修改从这些完成锚点之后继续，不得用换标题、换简介或换关键词的方式重复生成同一课义。

新建课程没有过去版本上下文，继续使用现有创建上下文。

## 服务端边界

`CourseAuthoring` 接收两个只读能力：

- `isLessonCompleted(lessonId)`：读取权威课时进度；
- `listCompletedLessonOutlineContexts(courseId)`：读取该课程所有已完成课时的冻结大纲概要。

本地运行时通过现有课程仓储和学习会话仓储实现这两个能力。候选生成协调器与发布事务共享同一完成判定，避免 Prompt 认为已完成而发布端认为未完成。

## 验收

- 修改大纲的 Prompt 中存在且只存在一个“过去版本上下文”区，其中严格包含“对话压缩”和“用户已完成课时概要”两部分。
- 两节完成课即使未被模型返回，也仍以原 `lessonId` 出现在发布后的活动课程中。
- 模型改写相同 `semanticKey` 时，持久化的仍是原冻结课义。
- 未开始、学习中和已放弃课时继续遵循现有规则。
- 当前课程活动课时以前述两个原完成课开头，不再包含两节新版重复课，模块二以后与修复前新版保持一致。
