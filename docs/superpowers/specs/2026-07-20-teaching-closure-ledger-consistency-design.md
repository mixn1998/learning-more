# 正式课程闭环与教学账本一致性设计

## 目标

修复“用户明确没有其他问题后，AI 已输出本课总结，但右侧教学账本仍停留在讨论答疑”的不一致。

正确业务语义是同一个闭环动作：

1. 用户明确表示没有其他问题。
2. 教学智能体输出最终课程总结。
3. 教学账本在一次原子提交中同时记录：
   - 讨论答疑已完成；
   - 本课总结已完成；
   - 课节已具备关闭条件。
4. 前端从同一账本快照投影两个完成节点，并允许用户结束本课。

## 已核验的故障事实

当前故障会话中，最终 AI 回复已经持久化，并且任务结果携带了正确控制指令：

- `lessonPhase = ready_to_close`
- `closureInquiry = confirmed_no_questions`
- `summaryStatus = delivered`

同一指令使用当前 reducer 和契约校验可正常得到闭环状态。因此故障不在提示词、控制协议、账本门禁或前端文案，而在回复提交后的编排与恢复：

1. 当前顺序先提交可见 AI 回复，再写教学账本。
2. 账本写入若发生版本冲突或瞬时失败，可见总结已经存在，但账本仍是旧状态。
3. 恢复逻辑把“已经存在 assistant message”视作任务已完整提交，排除了该任务，无法补写遗漏的教学指令。

这导致消息事实与账本事实产生永久分叉。

## 一致性约束

最终课程总结不能仅以“assistant message 已存在”作为完成依据。一次闭环生成只有同时满足以下条件才算完整：

- 最终回复内容通过解析与控制区校验；
- 教学指令已原子写入账本；
- 最终回复已提交到会话；
- 生成任务已进入完成终态。

教学账本中的答疑完成与总结完成不拆成两次写入。最终总结对应单次状态转换：

```text
lessonPhase: discussion        -> ready_to_close
closureInquiry: awaiting_*     -> confirmed_no_questions
summaryStatus: pending         -> delivered
```

因此前端的“讨论答疑”和“本课总结”会从同一个新账本版本同步变为完成，不能出现半闭环。

## 提交流程

最终回复生成完成后按以下顺序提交：

1. 解析并校验 AI 回复与结构化教学指令。
2. 基于最新教学账本应用指令。
3. 使用乐观并发控制持久化账本；遇到版本冲突时重新读取最新账本并有限次重放同一指令。
4. 账本提交成功后，提交最终 assistant message。
5. 回复与账本均成功后，才把生成任务标记为完成并广播完成事件。

教学指令是确定性的状态转换，重放必须保持幂等：目标状态已经存在时视为成功，不创建额外节点、不重复累计行为证据。

## 自动恢复

会话读取与任务协调不能仅检查“是否已有 assistant message”。对于最近一次已提交回复，还需要比较其持久化教学指令与当前账本：

- 回复已提交、指令未落账：自动重放该指令并修复账本；
- 回复和账本均已完成：不重复处理；
- 账本已经推进到更新阶段：不得用旧指令回退状态；
- 指令无效或与当前会话身份不匹配：保留现状并记录明确失败原因。

这一路径应自动修复现有故障会话，无需用户重新发送“没有了”或手动重试。

## 前端投影

前端不推断总结正文，也不根据文本匹配闭环。只消费服务端教学账本：

- `closureInquiry = confirmed_no_questions`：讨论答疑显示已完成；
- `summaryStatus = delivered`：本课总结显示已完成；
- `lessonPhase = ready_to_close`：结束本课门禁开放。

三个字段来自同一账本版本，因此 UI 不应出现总结已显示但节点未同步的中间稳定态。

## 验证范围

实现需覆盖：

1. 用户明确无疑问后，最终总结伴随答疑与总结两个节点同时完成。
2. 首次账本写入发生版本冲突时，重读并重放后仍完成闭环。
3. 回复已提交但账本未应用指令时，会话读取可自动修复。
4. 重复读取、重复协调不会重复写入或回退教学进度。
5. 现有故障会话恢复后，实时接口返回 `ready_to_close / confirmed_no_questions / delivered`。
