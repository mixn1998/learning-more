# Learning MORE 2.0 当前现状文档整体重写设计

## 1. 目标

整体重写 `docs/项目2.0现状`，使其成为 Learning MORE 当前产品与工程状态的权威入口，而不是开发历史、设计草案或未来路线图的混合记录。

重写后的文档必须让读者能够分别回答：

1. 产品现在允许用户完成什么任务；
2. 前端如何呈现这些能力；
3. 后端如何保证状态、数据、AI 任务和恢复；
4. 当前产品可被验收的正式需求是什么；
5. 已实现能力形成了什么价值，还有哪些真实缺口；
6. 产品视觉身份如何在实际界面中一致使用。

## 2. 事实基线

本次重写使用以下事实优先级：

1. 已提交基线 `f4bc470` 的生产装配和运行代码；
2. 共享合同、领域接口、状态机和持久化实现；
3. 前端实际路由、页面组合、客户端数据流和展示投影；
4. 自动化测试、类型检查、格式检查、架构门禁和构建脚本；
5. 重写完成时重新核验的活动 Runtime；
6. `CONTEXT.md` 中已经稳定的领域术语。

旧版现状文档、设计稿和实施计划只用于发现需要核验的线索，不直接作为当前能力的证明。

活动构建 ID、当前 Provider、具体模型和瞬时健康状态属于动态运行事实。文档可以记录核验结果，但不得把这些值写成永久产品常量。

## 3. 状态口径

所有现状文档统一使用四类状态：

- **已接入**：存在用户入口或正式 HTTP/后台入口，并进入生产装配。
- **条件接入**：已经进入生产装配，但只在指定 Provider、材料类型或运行条件下可用。
- **工程保障**：不直接形成用户功能，但已经用于一致性、恢复、性能或交付保障。
- **当前限制**：当前代码中可以确认的能力边界，不用未来设计代替事实。

已经提交但尚未通过生产装配抵达用户或后台主链的实验实现，不写成“已接入”。测试夹具、仅有类型定义的接口和未注册场景也不写成现有能力。

## 4. 文档信息架构

### 4.1 `README.md`

作为目录总入口，包含：

- 本次核验日期、提交基线和活动 Runtime 核验结果；
- 系统一句话定位和核心闭环；
- 当前完成度与主要限制；
- 七份文档的职责和阅读顺序；
- 事实来源、状态词和维护规则。

README 只给出全局摘要，不展开模块实现。

### 4.2 `01-功能设计层.md`

只回答产品和领域问题：

- 产品范围、课程模式和核心业务对象；
- 建课、大纲修改、已完成课时锚点、规划、学习、Review、补充学习、关闭和删除；
- 教学阶段、讨论答疑、语义闭环和状态机；
- 历史、周报、全局档案、证据和学习画像；
- AI 与确定性程序的职责边界。

不展开 React 组件、文件路径和具体 Repository 实现。

### 4.3 `02-前端实现层.md`

只回答界面和客户端实现问题：

- 路由与应用外壳；
- 页面数据加载、ETag/版本核对和无更新快速展示；
- 主页汇总、规划、历史统计、学习日历和上周回顾；
- 建课与大纲修改工作台；
- 正式学习、流式回复、暂停恢复和多窗口写入；
- 课时 Review 的知识图谱、核心思想、学习表现和可选邻接探索投影；
- 学习画像的用户友好标题、摘要和手动刷新状态。

后端完整文档与前端归纳投影必须明确区分。

### 4.4 `03-后端架构层.md`

只回答系统如何保证正确运行：

- Host、Launcher、Web、Server 和 Windows 任务调度器的进程拓扑；
- 模块化单体的生产装配和领域模块边界；
- HTTP、流式 Markdown 和结构化教学指令；
- 文件聚合、事件、事实、快照、源修订和缓存失效；
- Generation Runtime、16 个正式 AI 场景、Provider seam 和恢复；
- 教学账本、能力路由、个性化摘要、补充学习和 Review JSON 修复；
- 行为 Episode、会话聚合、全局语义档案、候选证据和画像；
- 周报、画像调度、幂等、并发、原子写入、备份和损坏恢复；
- 测试分层、类型检查、格式、构建、发布和激活门禁。

瞬时运行故障只能写在“核验结果”，不能被描述成架构常态。

### 4.5 `04-当前态产品需求文档PRD.md`

把当前产品还原成可验收需求：

- 用户、目标、非目标和产品原则；
- 从建课到长期个性化的核心旅程；
- 按功能域编号的当前需求；
- 每项需求只描述已经接入的行为和边界；
- 非功能要求与当前版本整体验收标准；
- 现有能力边界。

PRD 不包含优先级建议和未来方案。

### 4.6 `05-产品视角深度分析.md`

在事实基础上进行产品判断：

- 定位、用户问题、价值闭环和差异化；
- 当前体验强项与真实摩擦；
- 证据飞轮、信任模型和潜在护城河；
- 当前主要矛盾、指标建议和演进优先级；
- 明确区分“现状判断”和“尚未实现的建议”。

已被近期实现解决的旧缺口必须删除或改写，不继续沿用旧结论。

### 4.7 `06-品牌视觉规范.md`

从当前品牌组件和界面事实重写：

- 品牌含义、标识结构、色彩和尺寸；
- Logo、课程模式、学科、状态和页面业务标识的边界；
- favicon、应用外壳和品牌区的一致性要求；
- 组件职责和验收标准。

## 5. 去重与链接规则

- 同一事实只在最匹配的文档中完整解释一次。
- README、PRD 和产品分析通过链接引用功能或架构事实，不复制实现细节。
- 产品术语以 `CONTEXT.md` 为准；代码名只在前后端实现文档中出现。
- 当前限制必须说明影响和边界，但不混入实施计划。
- 不记录逐提交开发历史，不固化容易过期的测试数量、代码行数或活动构建 ID。

## 6. 重写方法

1. 为当前基线建立功能、路由、模块、任务、数据和运行事实清单；
2. 逐份重写，不在旧文档上追加零散补丁；
3. 每完成一份，检查与其余六份的术语和职责边界；
4. 全部完成后核验内部链接、标题结构、占位词、重复事实和过时限制；
5. 执行 Prettier、`git diff --check`，并复核活动 Runtime；
6. 将七份文档作为一个原子提交交付。

## 7. 非目标

本任务不修改产品代码、领域合同、数据文件或运行配置；不新增未来功能设计；不把未实现建议升级为产品承诺；不重写 `PROJECT_CONTEXT.md`、架构方案和阶段实施计划。

如果核验发现活动 Runtime 异常，只记录或单独修复运行问题，不通过修改文档掩盖异常。

## 8. 验收标准

- 七份文档均以 `f4bc470` 及其后本任务产生的纯文档提交为代码基线；
- 当前主要用户链路、11 个领域模块和 16 个 AI 场景都有正确归属；
- 已完成课时锚点、补充学习、Review 投影、语义档案、画像刷新、源修订缓存和 Host 激活等近期能力不再缺失；
- 不再保留已经被实现解决的旧缺口或与代码相反的描述；
- 产品事实、前端事实、后端事实、需求和产品建议互不混写；
- 无 `TBD`、`TODO`、失效相对链接、明显重复章节或动态值常量化；
- 格式检查与 `git diff --check` 通过。
