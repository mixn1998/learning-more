# 按改动范围验证设计

## 目标

让日常修改默认只验证本次改动可能影响的范围，同时保留完整仓库验证和发布门禁。测试选择必须可解释、可重复；不能因为工作区存在大量无关改动，就把它们全部纳入当前修改的验证。

本设计取代“`pnpm verify` 默认运行整个仓库静态检查、测试与构建”的旧规则。

## 命令分层

### `pnpm verify`

日常默认命令，执行按改动范围选择的验证。

调用者可以显式传入本次修改文件：

```text
pnpm verify -- <file> <file> ...
```

未传入文件时，命令读取 Git 中已暂存、未暂存和未跟踪的改动。工作区包含不属于当前任务的修改时，开发者或智能体必须显式传入本次触及的文件，不能借自动发现扩大验证范围。

### `pnpm verify:full`

执行原 `pnpm verify` 的完整仓库流水线：

- 格式检查；
- Lint；
- 全量类型检查；
- Schema、架构和等价性检查；
- 默认单元与轻量集成测试；
- 全量构建。

### `pnpm verify:release`

先执行 `pnpm verify:full`，再执行容量、恢复、浏览器和视觉等发布级专项门禁。

CI、发布、便携包构建和发布演练使用 `verify:full` 或更高层级，不依赖日常受影响验证替代完整门禁。

## 受影响验证的选择规则

验证工具先规范化并校验输入文件必须位于仓库内，然后输出“输入文件、选中检查、选择原因”。

### 格式与 Lint

- 对受支持的改动文件执行定向格式检查。
- 对受支持的 JavaScript、TypeScript 和 React 文件执行定向 Lint。
- 纯文档修改不触发源码 Lint、类型检查、测试或构建。

### 测试

- 直接修改的测试文件必须执行。
- 源码文件通过 Vitest 的依赖关系选择关联测试。
- 默认排除容量和恢复演练；只有显式修改这些测试或调用专项命令时才执行。
- 新文件尚未进入依赖图时，运行同目录或同模块中可识别的测试；若无法可靠定位，则给出明确升级原因，而不是静默宣称已覆盖。

### 类型检查

- 根据改动文件定位所属 workspace package。
- 检查该 package 及直接或间接依赖它的本地 package。
- 合同包、共享 UI 或其他公共包的改动必须覆盖其下游消费者。
- 根级 TypeScript 配置、workspace 配置或无法可靠归属的跨包源码改动升级为完整类型检查。

### 条件门禁

- 合同 Schema、OpenAPI 或相关生成规则改变时执行 Schema 检查。
- 模块边界、架构规则或相关目录改变时执行架构检查。
- 等价性登记或其执行报告规则改变时执行等价性检查。
- 构建、打包、运行时激活、workspace 依赖或构建配置改变时执行相关构建；无法安全缩小范围时执行完整构建。

## 升级原则

日常验证只在存在可说明的影响路径时扩大，不按“保险起见”机械执行全量。

以下情况升级到 `verify:full`：

- 发布、发布候选、便携包或部署前检查；
- 根级构建、workspace、测试选择器或验证规则本身发生变化；
- 持久化格式、迁移框架或跨模块公共合同发生无法可靠局部化的变化；
- 受影响分析无法确定安全边界；
- 用户明确要求全量验证。

普通业务缺陷、局部界面调整、提示词修改或模块内行为变化不因修改本身自动触发全量验证。

## 开发与智能体规则

每项修改按以下顺序取得证据：

1. 用最小测试复现缺陷或描述缺失行为；
2. 运行直接相关测试；
3. 运行 `pnpm verify -- <本次修改文件>`，补足关联测试和受影响类型检查；
4. 仅在满足升级原则时运行 `verify:full`。

验证报告必须区分“目标测试通过”“受影响验证通过”和“完整仓库验证通过”，不得用局部结果冒充全量结果。

## 失败与安全边界

- 输入为空且工作区无改动时，以成功状态退出并明确说明没有待验证文件。
- 输入包含仓库外路径或不存在路径时失败，不自动忽略。
- 某个工具无法形成可靠选择时，必须升级对应检查或失败并说明原因。
- 验证工具不得修改源码、格式化文件或启动长期驻留服务。
- 受影响验证失败时不自动转跑全量；先报告最小失败证据。

## 验收标准

- 局部前端修改不会默认执行全部服务端测试和全量构建。
- 合同包改动会检查合同包及受影响下游。
- 测试选择器或根级验证配置改动会升级为完整验证。
- 脏工作区中显式文件列表只验证当前任务的影响范围。
- `verify:full` 等价于修改前的完整 `verify`。
- `verify:release` 仍覆盖完整验证及全部发布专项门禁。
- CI 和发布流程不会误用局部验证作为最终质量门禁。
