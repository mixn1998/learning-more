# Learning MORE 汇总读模型快照与增量刷新设计

状态：已确认方向，待实施
日期：2026-07-18
范围：主页、课程规划、上周回顾、历史统计、学习日历

## 1. 问题与目标

当前五个汇总型页面在每次进入时都会重新请求数据。主页和排期查询还会遍历本地文件实体；历史统计和学习日历虽然读取的是既有投影，却没有利用 ETag 返回 `304 Not Modified`，前端也不会保留上一份成功结果。

当前数据规模下已经观测到：

- 主页热加载约 1.5–2.5 秒，响应约 242 KB；
- 排期查询约 1 秒，响应约 139 KB；
- 上周回顾快照本身约 15 ms，但整页被完整主页查询拖慢到约 2.1 秒；
- 历史统计和学习日历在 ETag 未变化时仍返回 `200 + 完整正文`；
- 历史页面每次重新读取 798 条历史事实，共 16 个顺序分页请求；
- 课程规划一次渲染约 342 张课节卡。

目标行为是：

1. 有最后成功快照时立即显示，不进入整页空白加载；
2. 后台只核对轻量版本；版本未变时返回 `304`，不下载、不解析、不替换状态；
3. 版本变化时才读取或重建新快照，并在完整校验后原子替换；
4. 首次访问且不存在任何快照时才显示整页加载；
5. 快照损坏或重建失败时继续显示最后成功快照，并明确标记陈旧或更新失败；
6. 页面只读取自身展示所需的数据，不以完整主页或全部历史作为通用目录查询。

## 2. 方案比较与决策

### 方案 A：仅增加前端内存缓存

优点是改动小。缺点是后端仍会全量扫描主页和排期文件，浏览器刷新或服务进程重启后仍然慢，也无法形成可靠的一致性恢复。该方案不能解决根因，否决。

### 方案 B：分层静态快照、条件请求与 stale-while-revalidate

后端维护可持久化汇总快照和轻量版本游标；前端维护最后成功快照并在后台发送条件请求。现有历史投影和周报直接补齐条件请求，主页和排期增加真正的快照读模型。该方案同时改善热导航、浏览器刷新和服务重启后的读取性能，并能沿用现有原子写入与投影恢复规则，采用。

### 方案 C：文件监听或 WebSocket 主动推送

能够减少轮询，但需要处理监听丢失、进程重启、连接恢复和跨页面订阅一致性。在单用户、本地优先 MVP 中收益不足，暂不采用。

## 3. 模块与 Interface

### 3.1 后端 `SummarySnapshot` Module

该 Module 隐藏源实体扫描、快照持久化、版本比较、并发重建和失败保留。外部 Interface 只暴露：

```ts
type SnapshotResult<T> = Readonly<{
  etag: string;
  freshness: 'current' | 'stale' | 'rebuilding';
  value: T;
}>;

interface SummarySnapshot<T> {
  current(): Promise<SnapshotResult<T>>;
  invalidate(revision: string): void;
}
```

Interface 不暴露文件路径、实体仓储、锁、重建队列或校验和。相同版本的并发读取必须共享同一个重建 Promise，避免缓存击穿。

实现维护以下快照：

- `home-dashboard`：主页所需草稿、课程摘要、课节摘要和有效排期；
- `planning-context`：课程规划所需课程和未完成、未放弃课节摘要；
- `schedule-view`：当前有效排期及集合版本；
- `catalog-index`：历史、日历和周报只读展示所需的课程/课节名称与标签。

历史事实、统计、日历和周报已经是持久化投影或不可变快照，不再复制一层新投影，只统一接入条件读取。

统计和日历现有合同仍不够深：前端目前必须读取全部历史事实才能计算页面展示。实施时升级为展示无损的投影合同：

- `StatisticsResponse@2` 在现有累计值之外保存按本地自然日的学习时长/完成数序列、按日期与学科的时长序列、按日期的关键互动发起/回应/跳过序列，以及按课程聚合的完成数、放弃数、学习时长和最近学习日期；
- `CalendarResponse@2` 的每日记录保存该日各完成课节的 `lessonId`、`courseId` 和准确学习秒数，不再要求前端回查 `LessonCompletedFact`；
- `catalog-index` 保存课程名称、状态、模式、学科标签以及课节名称、课程归属和生命周期，供统计课程清单、日历记录和周报记录解析用户可见名称。

这些投影保留当前 30 天、本年、全部和自定义时间范围，学科分布、互动回应率、课程归档清单、日历每日记录及抽屉入口的全部功能；只是把重复计算从每个页面调用方收进读模型 Module。

### 3.2 后端 `ReadRevision` Module

该 Module 在本地事务提交时按受影响数据域推进单调版本：

- `catalog`：草稿、课程、确认版大纲、课节定义；
- `learning`：课节进度、会话结果、推荐状态；
- `schedule`：排期及计划流确认结果；
- `facts`：历史、统计、日历投影游标；
- `weekly`：周报静态版本。

版本清单与业务写入一起原子提交。快照 ETag 使用所消费数据域版本的确定性组合，而不是请求时间、目录 mtime 或临时进程计数。

### 3.3 前端 `QuerySnapshotCache` Module

该 Module 统一处理内存快照、`sessionStorage` 最后成功快照、请求合并、条件重验证和失效。页面只声明查询键与加载器，不自行维护缓存协议。

```ts
interface QuerySnapshotCache<T> {
  read(): T | undefined;
  revalidate(signal?: AbortSignal): Promise<'unchanged' | 'updated'>;
  invalidate(): void;
  subscribe(listener: () => void): () => void;
}
```

缓存持久化必须带合同版本和 ETag，恢复时先通过共享合同解析；解析失败只丢弃该缓存，不影响后端权威数据。

## 4. HTTP 合同

所有汇总 GET 统一支持：

- 响应 `ETag`；
- 请求 `If-None-Match`；
- 未变化返回 `304`，无响应正文；
- 新快照返回 `200`、完整正文和新 ETag；
- `X-Projection-Status: current | stale | rebuilding`；
- `Cache-Control: private, no-cache`，允许条件验证但禁止共享缓存替代应用一致性逻辑。

端点调整：

- `GET /api/v1/home`：读取 `home-dashboard` 快照；
- `GET /api/v1/planning-context`：替代课程规划对完整主页的依赖；
- `GET /api/v1/schedule`：读取 `schedule-view` 快照；
- `GET /api/v1/catalog-index`：供历史、日历和周报解析展示名称；
- 现有 `/api/v1/history`、`/history/stats`、`/history/calendar`、`/weekly-reports/:key` 补齐真正的条件请求。

`generatedAt` 只表示快照生成时间，不参与版本判断，也不得因为每次 GET 改变而破坏缓存命中。

## 5. 页面数据流

### 5.1 通用流程

1. 页面从 `QuerySnapshotCache` 同步读取最后成功快照；
2. 有快照则立即渲染，并在后台携带 ETag 重验证；
3. `304` 时保持当前对象引用，避免无意义 React 重渲染；
4. `200` 时先解析完整合同，再原子替换缓存和页面状态；
5. 请求失败时保留旧快照，显示非阻塞更新提示；
6. 没有快照时才进入整页加载或错误状态。

### 5.2 页面专属查询

- 主页：只读取 `home-dashboard`；
- 课程规划：并发读取 `planning-context` 和 `schedule-view`，任一旧快照都可先显示；
- 上周回顾：读取周报快照和 `catalog-index`，不再读取完整主页；周报事实中已有名称时不重复查询索引；
- 历史统计：读取 `StatisticsResponse@2` 和 `catalog-index`，用日/学科/互动/课程聚合序列完成现有范围筛选和全部展示，不预加载原始历史与日历；
- 学习日历：读取目标年份 `CalendarResponse@2` 和 `catalog-index`，直接形成每日课节与准确耗时；打开课程总结抽屉时才读取该课程总结，不预加载原始历史；
- 历史分页：按 `asOfEventId + cursor` 缓存，不在统计或日历首屏循环拉取全部 16 页。

### 5.3 命令后的失效

成功命令优先用响应结果更新本地快照；无法局部更新时只失效受影响查询键。失效不清空当前 UI，而是触发后台重验证。

## 6. 快照一致性与恢复

- 快照文件使用现有原子写入策略保存，包含 schema、schemaVersion、ETag、来源版本、生成时间、校验和和数据正文；
- 服务启动时优先读取并校验最后成功快照；来源版本一致则直接使用；
- 来源版本领先于快照时，旧快照以 `stale` 提供，同时后台单飞重建；
- 无快照或快照损坏时同步重建一次；重建失败按现有运行中心规则报告降级；
- 新快照只有在全部源数据读取、合同解析和校验和生成成功后才替换旧快照；
- 删除课程、放弃课节和排期撤销必须推进相应版本，确保旧条目不能长期滞留；
- 投影重建不会反向写入学习事实，也不引入复杂内部事件总线。

## 7. 课程规划渲染

课程规划当前一次渲染全部可见课节。改为窗口化列表：

- DOM 中只保留视口及前后缓冲区内的课节卡；
- 筛选、选择日期、排期命令和无障碍名称保持不变；
- 清空筛选结果仍基于完整过滤集合，而不是当前 DOM 项；
- 端到端测试验证滚动后目标课节能够出现并操作。

## 8. 错误与用户可见状态

- `cold-loading`：没有任何成功快照，显示整页加载；
- `ready`：快照当前且后台无任务，不显示加载状态；
- `refreshing`：继续显示旧内容，可显示轻量“正在检查更新”；
- `stale`：继续显示旧内容并提示数据可能不是最新；
- `refresh-failed`：继续显示旧内容，提供重试，不清空页面；
- `cold-error`：仅在没有任何可用快照时显示整页错误。

## 9. 测试与验收

### 9.1 合同与 Module 测试

- 相同 ETag 的所有汇总 GET 返回 `304` 且正文为空；
- 版本变化后返回 `200` 和新 ETag；
- 同版本并发读取只触发一次快照构建；
- 构建失败保留上一快照；
- 服务重启后可以读取持久化快照；
- 损坏快照能够重建，且不会覆盖权威实体数据；
- 课程删除、课节状态变化和排期命令只失效相应数据域。

### 9.2 前端测试

- 有缓存时首次渲染直接出现内容，不出现整页 loading；
- `304` 不替换对象引用、不重渲染数据区；
- `200` 原子更新缓存和页面；
- 重验证失败保留旧内容；
- 历史统计不调用日历和全历史分页；
- 学习日历不调用完整主页和全历史分页；
- 上周回顾不调用完整主页；
- 统计优化前后的四种时间范围、学科分布、互动率和课程清单输出等价；
- 日历优化前后的每日完成课节、准确耗时、课程归属和抽屉入口输出等价；
- 课程规划窗口化后筛选、滚动、排期和清空行为等价。

### 9.3 性能门槛

在当前 10 门课程、344 个课节、279 条有效排期和 798 条历史事实的数据规模下：

- 有前端快照的页面在 100 ms 内显示已有内容；
- 本地无变化条件核对在 100 ms 内完成且不返回正文；
- 服务端持久化主页快照冷读目标不超过 250 ms；
- 课程规划两份快照冷读目标不超过 300 ms；
- 上周回顾、历史统计和学习日历不再等待 `/api/v1/home`；
- 无更新连续进入页面五次，不得再次出现整页 loading；
- 无更新连续请求不得扫描课程、课节、学习进度或排期实体目录。

## 10. 实施顺序

1. 建立通用 ETag/`If-None-Match` HTTP 工具及合同测试；
2. 建立前端 `QuerySnapshotCache` 与条件请求能力；
3. 迁移历史统计、学习日历和上周回顾，先消除不必要查询；
4. 建立 `ReadRevision` 和后端 `SummarySnapshot` Module；
5. 迁移主页、规划上下文和排期快照；
6. 完成课程规划列表窗口化；
7. 运行单元、合同、集成、端到端和性能回归；
8. 激活新构建并在真实 Host 上重复五次无更新热加载验收。

## 11. 非目标

- 不引入数据库、Redis、WebSocket、Service Worker 或复杂事件总线；
- 不改变课程、课节、Review、周报或学习画像的领域语义；
- 不把浏览器缓存作为权威数据源；
- 不以固定 TTL 替代数据版本；
- 不为了性能删除历史事实、Review 证据或恢复信息。
